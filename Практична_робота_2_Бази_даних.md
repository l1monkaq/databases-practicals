# Практична робота №2

**Дисципліна:** Бази даних  
**Тема:** Побудова ER-моделі предметної області  
**Предметна область:** Бібліотека  
**Група:** ІПЗ-41  
**Виконала:** Якимчук Єва

## Мета роботи

Навчитися визначати сутності, їхні атрибути, кандидатні ключі та зв'язки з текстового опису предметної області, а також представляти отриману концептуальну модель у вигляді ER-діаграми.

## 1. Обрана предметна область й початкові вимоги

Продовжую моделювання системи **«Бібліотека»** з практичної роботи №1. Система зберігає бібліографічні відомості про книги, обліковує фізичні примірники та зареєстрованих читачів. Бібліотекар реєструє нові книги, додає примірники, оформлює видачу та повернення. Для кожної видачі потрібно знати читача, конкретний примірник, відповідального працівника і дати видачі та повернення. Один примірник не може мати більше однієї активної видачі одночасно.

## 2. Аналіз іменників і дієслів із вимог

| Слова з опису | Категорія | Результат аналізу |
|---|---|---|
| книга, примірник, читач, працівник, видача | Кандидати в сутності | Усі п'ять стають самостійними сутностями, бо мають власні записи та ідентифікатори |
| назва, автор, ISBN, рік видання, жанр | Кандидати в атрибути | Властивості книги; автор у спрощеній навчальній моделі зберігається текстовим полем |
| інвентарний номер, стан | Кандидати в атрибути | Властивості фізичного примірника |
| ПІБ, номер читацького квитка, телефон, дата реєстрації | Кандидати в атрибути | Властивості читача |
| ПІБ, роль | Кандидати в атрибути | Властивості працівника |
| дата видачі, планова дата повернення, фактична дата повернення | Кандидати в атрибути | Властивості операції видачі |
| має, належить, отримує, видає, оформлює, повертає | Кандидати у зв'язки/операції | Книга має примірники; читач отримує примірник через видачу; працівник оформлює видачу; повернення фіксується датою у видачі |

Слова «бібліотека» й «система» описують предметну область у цілому, а не окремі обліковувані екземпляри; тому вони не створюють додаткових сутностей.

## 3. Словник даних: 5 сутностей, атрибути, домени та ключі

**Позначення:** PK — первинний ключ, FK — зовнішній ключ, UK — альтернативний (унікальний) кандидатний ключ. Домени подані у стилі SQL, але модель поки концептуальна.

### 3.1. Книга (`Book`)

| Атрибут | Домен / тип | Обмеження та призначення |
|---|---|---|
| `book_id` | INTEGER, додатне | PK, обов'язковий |
| `title` | VARCHAR(200) | Назва, обов'язкова |
| `author` | VARCHAR(150) | Автор або перелік авторів, обов'язковий |
| `isbn` | VARCHAR(17) | UK, ISBN-10 або ISBN-13 із можливими роздільниками; обов'язковий у межах навчальної моделі |
| `publication_year` | SMALLINT | Рік видання у допустимому діапазоні 1450–поточний рік |
| `genre` | VARCHAR(80) | Жанр, обов'язковий |

**Кандидатні ключі:** `book_id`, `isbn` (за умови унікальності ISBN у каталозі). Обраний PK: `book_id`.

### 3.2. Примірник (`Copy`)

| Атрибут | Домен / тип | Обмеження та призначення |
|---|---|---|
| `copy_id` | INTEGER, додатне | PK, обов'язковий |
| `book_id` | INTEGER, додатне | FK → `Book.book_id`, обов'язковий |
| `inventory_number` | VARCHAR(30) | UK, унікальний інвентарний номер, обов'язковий |
| `condition` | VARCHAR(20) | Одне зі значень: `доступний`, `ремонт`, `списаний`; фізичний стан, не статус поточної видачі |

**Кандидатні ключі:** `copy_id`, `inventory_number`. Обраний PK: `copy_id`.

### 3.3. Читач (`Reader`)

| Атрибут | Домен / тип | Обмеження та призначення |
|---|---|---|
| `reader_id` | INTEGER, додатне | PK |
| `full_name` | VARCHAR(150) | ПІБ, обов'язковий |
| `card_number` | VARCHAR(30) | UK, номер читацького квитка |
| `phone` | VARCHAR(20) | Контактний номер, може бути відсутнім |
| `registered_at` | DATE | Дата реєстрації, обов'язкова |

**Кандидатні ключі:** `reader_id`, `card_number`. Обраний PK: `reader_id`.

### 3.4. Працівник (`Employee`)

| Атрибут | Домен / тип | Обмеження та призначення |
|---|---|---|
| `employee_id` | INTEGER, додатне | PK |
| `full_name` | VARCHAR(150) | ПІБ, обов'язковий |
| `role` | VARCHAR(30) | `бібліотекар` або `адміністратор`, обов'язковий |

**Кандидатний ключ:** `employee_id`. Обраний PK: `employee_id`.

### 3.5. Видача (`Loan`)

| Атрибут | Домен / тип | Обмеження та призначення |
|---|---|---|
| `loan_id` | INTEGER, додатне | PK |
| `copy_id` | INTEGER, додатне | FK → `Copy.copy_id`, обов'язковий |
| `reader_id` | INTEGER, додатне | FK → `Reader.reader_id`, обов'язковий |
| `employee_id` | INTEGER, додатне | FK → `Employee.employee_id`, обов'язковий |
| `issued_at` | DATE | Дата видачі, обов'язкова |
| `due_at` | DATE | Планова дата повернення, не раніше дати видачі |
| `returned_at` | DATE або NULL | Фактична дата повернення; NULL означає активну видачу |

**Кандидатний ключ:** `loan_id`. Обраний PK: `loan_id`. Для перевірки дат потрібне правило `returned_at IS NULL OR returned_at >= issued_at`. Для одного `copy_id` допускається не більше одного запису з `returned_at IS NULL` (бізнес-обмеження, яке реалізують під час створення БД).

## 4. Зв'язки, кардинальність і обов'язковість участі

| Зв'язок | Ступінь | Кратність зліва → справа | Обов'язковість участі |
|---|---|---|---|
| Книга — Примірник | 1:N | Книга має `0..N` примірників; примірник належить рівно `1` книзі | Для книги необов'язкова (у каталозі може бути запис без примірників); для примірника обов'язкова |
| Примірник — Видача | 1:N | Примірник має `0..N` історичних видач; видача стосується рівно `1` примірника | Для примірника необов'язкова; для видачі обов'язкова |
| Читач — Видача | 1:N | Читач має `0..N` видач; видача належить рівно `1` читачеві | Для читача необов'язкова; для видачі обов'язкова |
| Працівник — Видача | 1:N | Працівник оформлює `0..N` видач; кожну видачу оформлює рівно `1` працівник | Для працівника необов'язкова; для видачі обов'язкова |
| Читач — Примірник (концептуально через Видачу) | M:N | Читач може отримати `0..N` примірників протягом часу; примірник може побувати у `0..N` читачів | Необов'язкова для обох; реалізується через `Loan` |

**Пояснення позначень:** `1` — рівно один; `0..N` — від нуля до багатьох; `1:N` — один-до-багатьох; `M:N` — багато-до-багатьох. Кратність історичних видач не означає можливості паралельної активної видачі того самого примірника.

## 5. Зв'язок M:N і проміжна сутність

Між читачами та фізичними примірниками існує часовий зв'язок **M:N**: один читач може багато разів позичати різні примірники, а той самий примірник протягом років може видаватися різним читачам. Без окремої сутності неможливо зберігати історію кожної операції та її дати. Тому додаємо **асоціативну сутність «Видача» (`Loan`)**, яка містить посилання на `Reader` і `Copy`, а також дати й відповідального працівника. Таким чином, M:N замінюється двома зв'язками 1:N (`Reader` → `Loan` та `Copy` → `Loan`).

## 6. ER-діаграма

Нотація: **Crow's Foot**, із явними підписами кратності `1` та `0..N` біля кінців ліній. «Лапка» позначає сторону «багато», риска — сторону «один». Сутність `Loan` виділено іншим кольором як проміжну. PK, FK і UK зазначено безпосередньо в блоках сутностей.

## Висновок

У практичній роботі я проаналізувала предметну область бібліотеки й виокремила п'ять сутностей: книгу, примірник, читача, працівника та видачу. Для кожної сутності визначила атрибути, їхні домени й можливі ключі. Встановила зв'язки між сутностями та зазначила їхню кардинальність і обов'язковість участі. Окремо розглянула зв'язок M:N між читачами і примірниками, який перетворила за допомогою проміжної сутності «Видача». Отриману структуру представила ER-діаграмою, яку можна використати на наступному етапі проєктування бази даних.

## Відповіді на питання для захисту

**1. Як відрізнити атрибут від сутності?** Сутність — це самостійний об'єкт обліку з власною ідентичністю (наприклад, читач), а атрибут — властивість цього об'єкта (наприклад, телефон читача). Якщо об'єкт має власні зв'язки, життєвий цикл або набір властивостей, його доцільно представити окремою сутністю.

**2. Що означає кардинальність 0..N?** Один екземпляр першої сутності може бути пов'язаний з нулем, одним або багатьма екземплярами другої. Наприклад, новий читач може ще не мати жодної видачі.

**3. Чому зв'язок M:N потребує окремого рішення?** У реляційній моделі прямий зв'язок «багато-до-багатьох» реалізують через проміжну таблицю. Вона зберігає пари зовнішніх ключів і атрибути самого зв'язку, як-от дату видачі.

**4. Чим нотація Чена відрізняється від Crow's Foot?** У Чена сутності показують прямокутниками, атрибути овалами, зв'язки ромбами. У Crow's Foot сутності зазвичай мають вигляд таблиць зі списками атрибутів, а кратність і обов'язковість показують позначками на кінцях ліній зв'язку.
