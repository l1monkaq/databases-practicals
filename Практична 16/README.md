## 2. Аналіз та класифікація підзапитів

### 2.1. Скалярний підзапит (Scalar Subquery)
* **Означення:** Повертає атомарне значення: рівно один рядок і один стовпець. Може використовуватися скрізь, де допускається константа або вираз.
* **Запит:** Пошук курсів, вартість яких перевищує середню по коледжу.
```sql
SELECT title, tuition_fee
FROM college.courses
WHERE tuition_fee > (SELECT AVG(tuition_fee) FROM college.courses);
```
* **Очікуваний результат:**
  * Середня вартість $\text{AVG} = (1200 + 1100 + 1300 + 950 + 850 + 1400) / 6 = 1133.33$ грн.

| title | tuition_fee |
|---|---:|
| Архітектура комп'ютерів | 1400.00 |
| Кібербезпека | 1300.00 |
| Бази даних | 1200.00 |

---

### 2.2. Багаторядковий підзапит із `IN`
* **Означення:** Повертає стовпець значень (множину), перевіряючи належність зовнішнього атрибута до цієї множини.
* **Запит:** Студенти, які зареєстровані на курси з кількістю кредитів $> 4$ (курси `PHY` (5) та `ARCH` (6)).
```sql
SELECT student_id, full_name
FROM college.students
WHERE student_id IN (
    SELECT e.student_id
    FROM college.enrollments e
    JOIN college.courses c ON e.course_id = c.course_id
    WHERE c.credits > 4
);
```
* **Результат:** `103 - Шевчук Анна` (курс `AST` не підходить, але `PHY` має 5 кредитів) та `105 - Бондаренко Денис` (курс `ARCH` має 6 кредитів).

---

### 2.3. Кванторні підзапити з `ANY` та `ALL`
Підмножина кредитів кафедри фізики (`department_id = 2`): $\{5, 3\}$.

| Оператор | Математична сутність | Умова в прикладі | Результат (курси) |
|---|---|---|---|
| **`> ANY (...)`** | Більше за **хоча б одне** значення з підмножини ($\text{val} > \min(S)$) | $\text{credits} > 3$ | `ARCH` (6), `PHY` (5), `DB` (4), `SEC` (4) |
| **`> ALL (...)`** | Більше за **всі** значення підмножини одночасно ($\text{val} > \max(S)$) | $\text{credits} > 5$ | `ARCH` (6) |

---

### 2.4. Корельований підзапит із `EXISTS`
* **Означення:** Вкладений запит звертається до стовпців зовнішнього рядка (`WHERE c.department_id = d.department_id`). Він обчислюється логічно для кожного зовнішнього рядка; `EXISTS` повертає `TRUE` у момент знаходження першого відповідного запису (Short-Circuit evaluation).
* **Запит:** Кафедри, що мають хоча б один курс із фактичними реєстраціями.
```sql
SELECT d.code, d.name
FROM college.departments d
WHERE EXISTS (
    SELECT 1
    FROM college.courses c
    JOIN college.enrollments e ON c.course_id = e.course_id
    WHERE c.department_id = d.department_id
);
```
* **Результат:** `IT` та `FIZ`. Кафедра `HUM` (Гуманітарні науки) відсіюється, бо не має курсів та реєстрацій.

---

### 2.5. Порівняння: Підзапит `IN` проти `JOIN`

Завдання: *Отримати список студентів, що вивчають «Бази даних»*.

```sql
-- Варіант 1: Підзапит IN (Semi-Join)
SELECT s.student_id, s.full_name
FROM college.students s
WHERE s.student_id IN (
    SELECT e.student_id FROM college.enrollments e
    JOIN college.courses c ON e.course_id = c.course_id
    WHERE c.code = 'DB'
);

-- Варіант 2: INNER JOIN
SELECT DISTINCT s.student_id, s.full_name
FROM college.students s
JOIN college.enrollments e ON s.student_id = e.student_id
JOIN college.courses c ON e.course_id = c.course_id
WHERE c.code = 'DB';
```

| Критерій | Підзапит `IN` | З'єднання `JOIN` |
|---|---|---|
| **Дублікати** | Гарантує унікальність студентів природно (працює як множина / Semi-Join). | Якщо студент випадково має кілька записів, `JOIN` розмножить рядки; потрібен `DISTINCT`. |
| **Оптимізація СКБД** | Сучасний планувальник PostgreSQL автоматично перетворює `IN` на оптимізований `Hash Semi Join`. | Виконує стандартний `Hash Join` із подальшим сортуванням або хешуванням для `DISTINCT`. |
| **Доступність колонок** | Доступні поля лише зовнішньої таблиці `students`. | Дозволяє вивести в `SELECT` стовпці обох таблиць (наприклад, оцінку `e.grade`). |

### 2.6. Підзапит у секції `FROM` (Похідна таблиця / Derived Table)
Дозволяє реалізувати багаторівневу агрегацію: спочатку порахувати кількість студентів на кожному курсі, а потім знайти середнє значення та розмах по всіх курсах:

```sql
SELECT ROUND(AVG(course_stats.enrollments_count), 2) AS avg_enrollments_per_course,
       MAX(course_stats.enrollments_count) AS max_enrollments_on_course,
       MIN(course_stats.enrollments_count) AS min_enrollments_on_course
FROM (
    SELECT c.course_id, COUNT(e.student_id) AS enrollments_count
    FROM college.courses c
    LEFT JOIN college.enrollments e ON c.course_id = e.course_id
    GROUP BY c.course_id
) AS course_stats;
```
* **Результат:** Середня кількість студентів на курс: $7 / 6 = 1.17$; максимум — $3$ студенти (курс `DB`); мінімум — $0$ (курси `AST`, `SEC`).

## 3. Відповіді на питання для захисту

1. **Чим скалярний підзапит відрізняється від багаторядкового?**
   Скалярний підзапит повертає виключно одне значення (1 клітинку: 1 рядок, 1 стовпець) і може використовуватись у виразах обчислень чи операторах порівняння (`=, <, >, <=, >=`). Багаторядковий підзапит повертає множину значень (1 стовпець, $N$ рядків) і вимагає застосування спеціальних предикатів множин (`IN`, `NOT IN`, `ANY`, `ALL`).

2. **Що відбувається, якщо скалярний підзапит повертає кілька рядків?**
   Виникає помилка часу виконання (Runtime Error): у PostgreSQL це `ERROR: more than one row returned by a subquery used as an expression (SQLSTATE 21000)`. Запит аварійно переривається.

3. **Коли доцільний `EXISTS` замість `IN`?**
   `EXISTS` є кращим вибором:
   * Коли підзапит оперує великими обсягами даних, оскільки `EXISTS` зупиняє сканування відразу після знаходження першого збігу (Short-Circuit), тоді як `IN` потенційно матеріалізує повний список.
   * Коли результат підзапиту може містити значення `NULL`. Для виразу `NOT IN (NULL, ...)` будь-яке порівняння повертає `UNKNOWN`, через що весь запит повертає порожній результат. `NOT EXISTS` коректно працює з `NULL`, оскільки перевіряє факт наявності кортежу, а не рівність значень.

4. **Чому корельований підзапит виконується для кожного зовнішнього рядка?**
   Корельований підзапит містить змінні (посилання на стовпці), які беруться із зовнішнього запиту. Оскільки значення цих параметрів змінюються від рядка до рядка зовнішньої таблиці, підзапит не можна обчислити один раз заздалегідь: він концептуально переобчислюється для кожного поточного рядка (хоча планувальник СКБД часто трансформує його у Hash Join або використовує кешування результатів).
