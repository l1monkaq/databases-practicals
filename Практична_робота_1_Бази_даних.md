# Практична робота №1

**Дисципліна:** Бази даних  
**Тема:** Моделювання даних і вибір підходу  
**Предметна область:** Бібліотека  
**Група:** ІПЗ-41  
**Виконала:** Якимчук Єва  

## Мета роботи

Навчитися описувати предметну область, визначати факти, які необхідно зберігати в базі даних, порівнювати різні моделі даних і обґрунтовувати вибір моделі для конкретної інформаційної системи.

## 1. Вибір предметної області

Для моделювання обрано предметну область **«Бібліотека»**. Інформаційна система бібліотеки призначена для обліку книг, їхніх фізичних примірників, читачів і операцій видачі та повернення. Система дає можливість швидко знаходити книги, перевіряти їхню доступність і контролювати строки повернення.

## 2. Опис предметної області

**Користувачі системи:**

- **Бібліотекар** — реєструє книги та примірники, оформлює видачу й повернення, переглядає прострочені видачі.
- **Читач** — шукає книги в каталозі, переглядає доступність примірників і власні активні видачі.
- **Адміністратор** — керує обліковими записами працівників, правами доступу та налаштуваннями системи.

**Основні об'єкти:**

1. **Книга** — бібліографічний запис про видання (назва, автор, ISBN, рік видання, жанр).
2. **Примірник** — конкретна фізична одиниця книги з інвентарним номером і станом.
3. **Читач** — людина, зареєстрована в бібліотеці.
4. **Видача** — факт передавання певного примірника читачеві на визначений строк.
5. **Працівник** — бібліотекар, який оформлює операцію.

**Операції, які повинна підтримувати система:** додавання та редагування записів про книги; реєстрація примірників; пошук за назвою, автором або ISBN; реєстрація читачів; видача й повернення примірників; перевірка наявності примірників; перегляд історії видач і переліку прострочених повернень.

**Основні правила:** один бібліографічний запис може мати багато примірників; примірник може мати багато видач протягом часу, але не більше однієї активної видачі одночасно; кожна видача пов'язана з одним читачем, одним примірником і бібліотекарем.

## 3. Факти, які потрібно зберігати

| Об'єкт | Факти (атрибути) |
|---|---|
| Книга | ID книги, назва, автор, ISBN, рік видання, жанр |
| Примірник | ID примірника, ID книги, інвентарний номер, стан примірника |
| Читач | ID читача, ПІБ, номер читацького квитка, телефон, дата реєстрації |
| Видача | ID видачі, ID примірника, ID читача, ID бібліотекаря, дата видачі, планова дата повернення, фактична дата повернення |
| Працівник | ID працівника, ПІБ, роль |

Кожен об'єкт має унікальний ідентифікатор (ID). Зв'язок примірника з книгою зберігається через `ID книги`, а зв'язки видачі — через ідентифікатори примірника, читача та бібліотекаря. Це дає змогу уникати повторного введення одних і тих самих відомостей.

## 4. Два сценарії роботи системи

### Сценарій 1. Додавання нової книги

Бібліотекар отримує нове видання та вносить його до каталогу.

1. Перевіряє, чи є книга з таким ISBN у каталозі.
2. Якщо бібліографічного запису ще немає, створює запис **Книга**: назва, автор, ISBN, рік і жанр.
3. Створює запис **Примірник**: посилання на книгу, унікальний інвентарний номер і стан «доступний».
4. Якщо книга вже є в каталозі, створює тільки новий примірник і не дублює бібліографічні дані.

**Створюються/змінюються факти:** новий ID книги та її атрибути (якщо книги ще не було); ID примірника, ID книги, інвентарний номер, стан примірника. Дані читача й видачі не змінюються.

### Сценарій 2. Видача книги читачеві

Читач просить книгу, а бібліотекар оформлює видачу доступного примірника.

1. Система перевіряє, чи зареєстровано читача.
2. Перевіряє, чи існує примірник і чи немає для нього активної видачі.
3. Створює запис **Видача**: ID видачі, ID примірника, ID читача, ID бібліотекаря, дата видачі та запланована дата повернення.
4. У записі видачі поле фактичної дати повернення залишається порожнім до повернення книги.
5. Доступність примірника визначається за відсутністю або наявністю активної видачі; окремий прапорець доступності не потрібен, щоб не допустити суперечливих даних.

**Створюються/змінюються факти:** створюється запис видачі з усіма відповідними зв'язками та датами. Записи книги, примірника й читача залишаються незмінними.

### Таблиця «об'єкт — факт — сценарій»

| Об'єкт | Факт | Сценарій 1: додавання книги | Сценарій 2: видача книги |
|---|---|---|---|
| Книга | ID, назва, автор, ISBN, рік, жанр | Створюються, якщо книги ще немає | Не змінюються |
| Примірник | ID примірника, ID книги, інвентарний номер | Створюються | Використовуються для зв'язку з видачею |
| Примірник | Стан примірника | Задається «доступний» | Не змінюється; доступність перевіряється за активними видачами |
| Читач | ID, ПІБ, читацький квиток | Не змінюються | Використовуються для встановлення читача |
| Працівник | ID працівника | Використовується працівником системи | Записується як ID бібліотекаря у видачі |
| Видача | ID видачі, ID примірника, ID читача, ID бібліотекаря | Не створюються | Створюються |
| Видача | Дата видачі, строк повернення, фактична дата повернення | Не створюються | Дати видачі й строку записуються; фактична дата поки порожня |

## 5. Порівняння підходів до моделювання даних

| Модель даних | Як описує бібліотеку | Сильна сторона | Слабка сторона |
|---|---|---|---|
| **Ієрархічна** | Дані розташовані у дереві, наприклад «Книга → Примірники». | Зручна для простих відношень «батько — нащадок». | Важко описати зв'язки видач одночасно з читачами й примірниками без дублювання або складних обхідних рішень. |
| **Мережева** | Книги, читачі та видачі пов'язані набором посилань. | Добре підтримує складні взаємозв'язки між записами. | Складніше розробляти, змінювати структуру й супроводжувати систему. |
| **Реляційна** | Книга, Примірник, Читач, Видача і Працівник — окремі таблиці, пов'язані ключами. | Забезпечує цілісність зв'язків, зручні запити SQL та контроль дублювання. | Для отримання повної інформації про видачу часто потрібні JOIN між кількома таблицями. |
| **Об'єктна** | Книга, Читач та Видача представлені об'єктами з властивостями й методами. | Природно відповідає об'єктно-орієнтованій логіці застосунку. | Менш універсальна для стандартних табличних звітів і SQL-інструментів. |
| **Документна** | Записи зберігаються як документи JSON, наприклад документ книги з переліком примірників. | Гнучка структура; легко додавати необов'язкові властивості видань. | Посилання між читачами, примірниками та видачами й узгодженість даних потребують додаткового контролю. |
| **Ключ–значення** | За ключем `book:123` або `reader:45` зберігається значення з даними. | Дуже швидкий доступ до конкретного запису за ключем. | Незручна для пошуку за кількома полями, складних зв'язків та аналітичних звітів. |

## 6. Обґрунтування вибору моделі даних

Для бібліотечної системи найкраще підходить **реляційна модель даних**. У цій предметній області є чітко визначені об'єкти та зв'язки між ними: одна книга має багато примірників, а один читач може отримувати різні примірники в різний час. Реляційна база дає змогу розділити ці відомості на таблиці, задати первинні та зовнішні ключі, а також контролювати цілісність даних. За допомогою SQL можна шукати книги, знаходити активні видачі та створювати звіти про прострочення. Ієрархічна й мережева моделі менш зручні для розвитку цієї системи, об'єктна ускладнює стандартну звітність, а документна та модель «ключ–значення» потребують додаткового контролю зв'язків. Тому для реалізації доцільно використати реляційну СКБД, наприклад PostgreSQL або SQLite.

Її використання допоможе уникнути зайвого дублювання інформації та спростить пошук і облік книг. Отже, поставленої мети роботи досягнуто.

## Відповіді на питання для захисту

**1. Чим дані відрізняються від інформації та знань?**  
Дані — це окремі факти, наприклад дата видачі `03.11.2026`. Інформація — це дані, опрацьовані в контексті, наприклад повідомлення «читач отримав книгу 3 листопада». Знання — це розуміння закономірностей і правил, що допомагає ухвалювати рішення, наприклад правило, за яким система визначає прострочену видачу.

**2. Які функції СКБД знадобляться для обраної системи?**  
Створення й редагування таблиць; додавання, пошук, оновлення й видалення записів; підтримка первинних і зовнішніх ключів; обробка транзакцій, щоб видача оформлювалася коректно; розмежування прав доступу; резервне копіювання та відновлення даних.

**3. Чому один і той самий факт може бути збережено з помилкою за кількома адресами?**  
Якщо дублювати, наприклад, телефон читача в багатьох записах видачі, то після його зміни частина записів може залишитися зі старим номером. Така ситуація називається аномалією оновлення. Щоб цього уникнути, дані про читача зберігають в одному місці, а з видачі посилаються на його ID.

**4. Які критерії використали для вибору моделі даних?**  
Характер зв'язків між об'єктами, цілісність даних, відсутність зайвого дублювання, зручність пошуку та звітів, простота підтримки, можливість розвитку системи й наявність відповідних інструментів.
